# 实施复盘

当前结果以docs/03-evaluation.md和06-submission-checklist.md的实际核对为准。离线和DeepSeek真实运行均保存实际Trace及失败归档；GitHub继续等待用户命令。

## 主要难点与处理

1. 引用真实不等于答案有依据。采用原文摘录式答案与已读引用校验缩小风险，仍需评估引用与问题的相关性。
2. 文档版本新不等于优先级高。没有明确适用范围和替代关系时，30天/15天制度必须并列显示冲突。
3. Agent循环不能只表现为固定条件分支。真实接口接收工具观察后输出下一步动作；离线Mock只验证循环基础设施，不能替代真实模型验收。
4. 测试不能只看最终一句话。需要检查工具序列、未读候选、故障后的参数变化、终态和Trace一致性。

## 实际失败及学习收获

第一轮44项测试有1项失败：检索层能通过别名把annual leave映射为年假，但Mock意图层没有相同处理，最终错误返回资料不足。修复意图映射后保留该用例，并补充CLI从不同目录运行的检查，最后共48项通过。

这个问题说明“召回成功”和“动作选择正确”需要分开验证；只检查工具有命中或只看正常演示，都会漏掉错误。后续接入真实模型时应同样观察它是否选择正确主题、读完同主题冲突候选，以及是否据故障结果调整下一步。

真实模型测试进一步暴露了Mock没有证明的两个问题：把历史塞在JSON里不一定能被模型正确用于追问；过度强调缺信息澄清，又可能让有历史的正常问题停住。改为正式多轮消息，并明确身份、业务主题及历史指代的关系后，必须把“有历史可继续”和“无主题要澄清”成对复测。原来的失败记录保留，不能只提交成功演示。

取舍方面，原文摘录和事实值校验牺牲了一部分表达自由，换来可直接核验的数字、单位和引用。有限域事实标注适合本次验收，但不能代替开放域语义冲突识别，这也是下一阶段需要真实模型样例验证的部分。

## 下一步

下一步在用户下令后上传GitHub并补齐URL、最终commit SHA及评审访问权限。质量改进方向是增加真实模型多轮重复、不同措辞、未标注冲突和恶意资料测试，再评估更强检索及企业权限；不把单轮场景通过等同生产可靠性。
